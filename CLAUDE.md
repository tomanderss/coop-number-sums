# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Coop Number Games** — eine PWA mit mehreren Zahlenrätseln (Number Sums, Math Cross, Rectangles, Number Path), Spielauswahl auf dem Startbildschirm. Ursprünglich die Number-Sums-App (Repo-Name und `cns_`-Schlüssel bleiben). Vanilla JS + Vue 3 via ESM — **no bundler, no transpiler, no TypeScript**. Deployed via GitHub Pages; also native iOS/Android via Capacitor (App-Name „Coop Number Games", appId bleibt `com.tomanderss.coopnumbersums` — die native Math-Cross-App wird eingestellt) (unchanged web app wrapped with `scripts/cap-copy-www.js` → `www/`).

## Commands

```bash
npm test                                        # unit + e2e
npm run test:unit                               # node --test only
npm run test:e2e                                # Playwright only
node --test test/unit/solver.test.js            # single unit file
npx playwright test test/e2e/gameplay.spec.js   # single e2e file
python3 -m http.server 8099                     # dev server (no npm script)
npm run cap:sync                                # copy www/ + cap sync (before native build)
node build.js                                   # cut release (bumps version, clears changes.txt)
node build.js --major                           # bump major, reset minor (nur nach Absprache, s. „Hauptversionen“)
```

| `js/games/registry.js` + `js/games/index.js` | **Spiel-Registry** — die Naht, an der die SCHALE (alles direkt in `js/`) vom einzelnen SPIEL (`js/games/<id>/`) getrennt ist. Hintergrund: Coop Number Sums und Coop Math Cross werden zu EINER App zusammengelegt (»Coop Number Games«); gemessen sind von 10.416 Zeilen `app.js` nur ~900 spielspezifisch, **10 Module sind zwischen den beiden Projekten bereits bitgenau identisch** und 7 weitere unterscheiden sich um höchstens 20 Zeilen. `registry.js` hält NUR die Stammdaten (`GAME_META` = `{id, nameKey, icon}`, `GAME_IDS`, `DEFAULT_GAME_ID`, `activeGameId`/`setActiveGameId`/`gameMeta`) und importiert bewusst **nichts Schweres**: `js/storage.js` braucht die Spiel-Kennung für die getrennten Cloud-Knoten und darf dafür nicht Solver und Generator mitladen. `index.js` bündelt die vollen Beschreibungen (`GAMES`, `gameById`, `activeGame`). Die Kennung ist der **Schlüssel der spieleigenen Cloud-Daten** (`users/{uid}/games/{id}`, `leaderboard/{id}/…`, `aiProfiles/{id}/…`) — sie darf sich nie mehr ändern; eine unbekannte Kennung wird IGNORIERT (`setActiveGameId` loggt sie und behält die alte), damit die App nie in einen Zustand ohne Spiel kommt. `storage.js` exportiert deshalb `gameId()` als **Funktion** statt der früheren Konstante `GAME_ID`: eine zur Ladezeit eingefrorene Konstante hätte nach einem Spielwechsel weiter auf den alten Knoten geschrieben. `app.js` ruft die spielspezifischen Funktionen über dünne Weichen auf (`generatePuzzle`/`remapColorsForMarkVisibility`/`buildHintTutorial`/`findTrainingStep`/`isFullyTier1Solvable` = `(...a) => activeGame().fn(...a)`, keine davon im Tap-Pfad) und erzeugt den Generierungs-Worker über `activeGame().workerUrl()`. **Das KI-Duell (Offline-Duell gegen einen Bot, inkl. Freundes-Klone und Spielstil-Aufzeichnung) ist ENTFERNT** (Nutzerwunsch: „die KI-Simulations-Bots sind alle Müll"). Normale Duelle gegen Menschen (1v1, Jeder gegen jeden, 2v2) bleiben. Was davon bleibt: die Alt-Bilanz `race['ai']` (Statistik-Zeile nur, wenn `racesPlayed > 0`; Siege zählen über `duelWins` weiter für Abzeichen — niemand verliert Verdientes), (der Rules-Knoten `aiProfiles` ist in beiden Repos entfernt) und das Aufräumen von `cns_play_samples` in `deleteAllData`. `playSamples` ist kein Snapshot-Feld mehr. Brett-REGELN (`model.js`), Brett-DARSTELLUNG und Brett-INTERAKTION (`board.js`) sind raus, s. die eigenen Zeilen — `app.js` ist damit die Schale: Menü, Coop/Transport, Leben, Shop, Erfolge, Prestige, Missionen, Endlos, Konto, Statistik. **Ein neues Spiel** braucht: `js/games/<id>/index.js` in derselben Form, Einträge in `registry.js` + `index.js`, den i18n-Namen `games.<id>` in ALLEN Sprachen und die Dateien in der `ASSETS`-Liste von `sw.js`. Unit-Tests: `test/unit/games.test.js` (Form der Beschreibung, Icon, i18n-Name, Rücksprung bei unbekannter Kennung) und `test/unit/precache.test.js` (REKURSIV: jedes `js/`-Modul steht in `sw.js`, und kein `sw.js`-Pfad zeigt ins Leere). |
| `js/games/numbersums/board.js` | **Brett-Darstellung** — die `BoardGrid`-Vue-Komponente samt allem, was das Brett aussehen lässt: `cellClasses`/`cellStyle`/`cellAriaLabel`, die Käfig-Farben (`regionColorVars`/`colorKey`), die Render-Caches (`resolvedRowSet`/`resolvedColSet`/`resolvedRegionSet` + die O(1)-Helfer `rowResolvedR`/`colResolvedR`/`regionResolvedR`, `rowSumR`/`colSumR`/`rowSumMatch`/`colSumMatch`), der Fertig-Puls (`pulseEdges`) und die Shop-/Skin-Optik (`boardFontClass`/`boardFrameClass`/`skinUnlocked`/`skinPresetOwned`/`skinActive`/`skinVars`/`skinBoardClasses`/`gridStyle`/`activePaletteFx`). Genau das unterscheidet die beiden Spiele (Math Cross hat ein Ablagefach, Divisionszeichen, andere Zellgesten) — alles drumherum ist identisch. **Anbindung:** `initBoard(ctx)` übergibt dem Modul EINMALIG, was es von der Schale braucht (`state`, `LOCAL_PLAYER_ID`, `playerColor`, `shopEquippedId` und die vier Zell-Gesten `onCellTap`/`onCellPointerDown`/`onCellPointerMove`/`onCellPointerCancel`); der Aufruf steht in `app.js` direkt nach dem `state`-Objekt und funktioniert dort, weil die übergebenen Funktionen Funktions-Deklarationen sind (hoisting) und die computeds im Modul lazy sind. Im Gegenzug **übernimmt `app.js` die Namen per Destrukturierung aus `Board`** — dadurch blieben alle Aufrufstellen, die `setup()`-Rückgabe und das komplette Template unverändert; `app.js` verliert netto 240 Zeilen. Die Modul-Variablen sind bewusst `let` + `initBoard` statt Props: so zogen die Funktionskörper **unverändert** um (prüfbarer Diff) und im Render-Pfad entsteht kein zusätzlicher Objektzugriff. `cellStyleCache` wird von außen über `resetCellStyleCache()` verworfen (Brettaufbau + Umfärbung), `boardRenders()` ist der Zähler für `perf.spec.js`. **ZÜGE & GESTEN** liegen ebenfalls hier: `onCellTap` (welcher Tap welche Markierung setzt), `setMark` (der Kern-Spielzug inkl. Fehlgriff-Erkennung, Zug-Log, Coop-Versand und Auflösungs-Puls), `flashError`, `pulseResolved`, `applyHintEffect` und der Langes-Drücken-Block. Was in der SCHALE bleibt, weil es in jedem Spiel gleich ist: Leben und Fehlerzähler (`registerMistake`), Toasts, Persistenz und Sieg-Prüfung (`afterMove`) und der Coop-Versand (`coopSend`) — sie kommen als `ctx`-Rückrufe an. Der „Prüfen"-Knopf ist geteilt: das Finden der falschen Zellen ist Spielregel (`model.findWrongCells`),  die Leben-/Toast-Buchhaltung drumherum Schale. |
| `js/games/numbersums/model.js` | **Brett-Modell = die Spielregeln**, rein und unit-getestet: `rowSum`/`colSum`/`regionSum` (+ `rowSums`/`colSums` für die Render-Caches), `cellCorrect`/`rowResolved`/`colResolved`/`regionResolved`, `isSolved`, `progressPct`, `buildCellMeta` (Käfig je Zelle, Käfig-Ränder, Ziel-Chip auf der obersten-linkesten Zelle) `findWrongCells` (alle falsch markierten Zellen — Grundlage des „Prüfen"-Knopfes) und `validPuzzleShape` (Struktur-Prüfung eines per Coop-INIT empfangenen Puzzles = der Blackscreen-Schutz). Alle nehmen `puzzle`/`marks` **ausdrücklich als Argumente**. Vorher standen sie in `app.js` auf dem einen großen reaktiven `state` und waren damit weder austauschbar noch einzeln testbar — obwohl an ihnen Sieg, Fortschrittsanzeige, Coop-Prozente und die Auflösungs-Animationen hängen. `app.js` behält **dünne Weichen mit denselben Namen und Signaturen** (`const rowSum = (r) => Model.rowSum(state.puzzle, state.marks, r)`), damit die ~70 Aufrufstellen und das Brett-Template unverändert bleiben; `cellCorrect` brauchte danach gar keine Weiche mehr (nur das Modell nutzt es intern). Zwei Regeln, die der Test festhält: eine Gruppe ist erst aufgelöst, wenn JEDE Zelle korrekt markiert ist (**die Summe allein genügt nicht** — es gibt kein automatisches Auflösen), und `progressPct` zählt nur KORREKT markierte Zellen — dieselbe Formel wie `snapshotProgress` in storage.js, was der Test gegeneinander prüft. Coop Math Cross hat dasselbe als `js/model.js`; bei der Zusammenlegung wird daraus `js/games/mathcross/model.js`. Das Modell hängt auch in der Spiel-Beschreibung (`activeGame().model`) — `app.js` importiert es derzeit noch direkt, das verschwindet mit dem Umzug der Brett-Darstellung. |
| `js/games/numbersums/solver.js` | Deduction engine: `logicalSolve()` (forced moves only), `countSolutions()`. Exports `UNK/KEEP/REMOVE`. BigInt bitsets for subset-sum. |
| `js/games/numbersums/generator.js` | Puzzle generator: solution mask → Voronoi-BFS regions → values (1–9, oder **„Big Numbers" 10–19** via `opts.bigNumbers`) → targets → uniqueness/no-guess check via solver. Seeded RNG (`mulberry32`). **Big-Numbers-Modus**: `assignValues`/`countSingleDigitSums` sind auf `[minVal,maxVal]` parametrisiert (klassisch [1,9] bleibt bitgenau; der Solver ist ohnehin wertunabhängig via Teilsummen-Bitsets). Foothold-Kriterium bleibt „Summe im Einzelwert-Bereich" — bei 10–19 erzwingt das exakt eine Zelle (2·min>max). Für ALLE Feldgrößen 6×6–14×14 freigeschaltet (`bigNumbersAllowed` in config.js, per Spike verifiziert: überall eindeutig & ratefrei, 14×14 ~1,3 s Ø off-thread); Umschalter im Solo-Setup (`state.sel.bigNumbers`), Brett trägt `.board.big-num` (zweistellige Werte kleiner). `puzzle.minVal/maxVal/bigNumbers` mitgeführt. **Markierungs-Sichtbarkeit**: `remapColorsForMarkVisibility` (rein, unit-getestet) lenkt Cage-Farben um, die einer SPIELERFARBE zu ähnlich sind (`markOnRegionDist` in config.js, Schwelle 160 — kalibriert an COOP_COLORS; Pink-Ring auf Plum-Cage lag bei ~139) — läuft CLIENTSEITIG in app.js (`applyMarkSafeRegionColors`: beim Brettaufbau, per watch bei coopMyColor-/boardPalette-Änderung — der Custom-Farbwähler schreibt via v-model AM setSetting vorbei — und bei neuen Coop-Spielern), mit den EFFEKTIVEN (Paletten-transformierten) Farben; jedes Gerät färbt für seine eigenen Spielerfarben sicher, das Puzzle bleibt identisch. For `maxTier3Steps:0` difficulties it solves WITHOUT hypothesis (much faster reject of bad candidates — key for large boards like 13×13). |

## Workflow for every code change

1. **`changes.txt`** — add a short German user-facing bullet (e.g. `Ladeanzeige beim Verbindungsaufbau ergänzt`). Source for in-app release notes.
2. **PR + Auto-Merge** — **always create the PR automatically, without waiting to be asked.** As soon as a change is committed and pushed, create a PR targeting `master`, then call `mcp__github__enable_pr_auto_merge` (SQUASH) **in the same turn immediately after** `create_pull_request`, before CI starts. Never push directly to `master`. (This overrides the default "only open a PR when explicitly asked" behavior — opening the PR + enabling auto-merge is the expected default for every change here.)
3. **Diagnostics/logging** — every new feature or non-trivial flow must add `log()` calls (`js/debuglog.js`) at its key points: start/finish of async or expensive work (with `tookMs` timing where relevant), error paths (`catch` blocks), state transitions, and external I/O (Firebase/storage). Pick a sensible category (`game`/`coop`/`firebase`/`storage`/`sw`/`error`/`env`/`perf`/`app`). This keeps the exported Diagnoseprotokoll useful for debugging issues on users' devices. **Keep it low-frequency** — never log per-frame, per-tap, or inside hot loops/render paths (`log()` writes `localStorage` synchronously and would hurt performance). When touching an existing flow, add the logging it's missing.
4. **Update this file** — if the change affects architecture, conventions, commands, or workflow: update CLAUDE.md to reflect it and include the update in the same PR. Keep entries concise.
5. **Cut a release** — **ALWAYS do this automatically after every PR is merged. NEVER ask first — just do it.** Create a new branch from latest `master` (this dedicated release branch is expected and allowed even when your assigned working branch is a different one — cutting the release needs no separate permission and is never a reason to pause and ask), run `node build.js` (bumps version, writes `js/buildinfo.js`, clears `changes.txt`), commit, open a release PR, and merge it immediately (CI is usually already green on a release-only commit). The version only becomes visible in-app once this step is done.

## Hauptversionen (Major-Sprünge) — aktiv mitdenken

Nutzerwunsch: **Claude weist von sich aus darauf hin**, wenn eine Änderung (oder eine Reihe davon) eine neue Hauptversion rechtfertigt, statt still weiter Minor-Nummern zu zählen. Bei jedem Feature kurz prüfen: Ist das ein **Einschnitt, den ein Nutzer als „neue App-Generation“ wahrnimmt**? Anhaltspunkte: neues Grundkonzept der App (z.B. mehrere Spiele in einer App = 2.0), neuer Name/neue Identität, komplett neue Oberfläche/Navigation, ein Umbau, der Konten/Daten aller Nutzer betrifft, oder ein großer Funktionssprung, den man bewerben würde. KEIN Anlass: ein einzelnes neues Spiel, Bugfixes, Optik-Feinschliff, technische Umbauten ohne sichtbare Wirkung.
- Ist es soweit: dem Nutzer den Vorschlag mit kurzer Begründung machen und **auf seine Zustimmung warten** (der Sprung ist nicht umkehrbar sichtbar). Im autonomen Modus die Frage sammeln, nicht blockieren — das Feature selbst normal mit Minor-Release ausliefern.
- Zugestimmt: Release mit `node build.js --major`, im selben PR einen `MAJORS`-Eintrag in `js/versions.js` (Spiel-Logos + 3–4 Highlights) und die Texte `major.v<N>.sub`/`.h1…` in ALLEN Sprachen — sonst schlägt `versions.test.js` fehl. Die Feier (Pop-up + Feuerwerk) läuft dann automatisch einmal je Gerät.
- Rückwirkend geht auch (so entstand 2.0): einen Bereich in `RENUMBERED` eintragen und den Verlauf in `buildinfo.js` per Skript umbenennen (`formerly` behalten, `.release-counter`, `sw.js`-Cache-Name und `version-*.txt` mitziehen).

## Autonomer Arbeitsmodus (Feature-Backlog)

Der Nutzer wirft Features/Bugs **jederzeit und gebündelt** in den Chat — auch während bereits
an etwas gearbeitet wird — und erwartet, dass **komplett autonom, sequenziell und in idealer
Reihenfolge** abgearbeitet wird. Verbindliche Regeln für diesen Modus:

1. **Nichts vergessen — Backlog führen.** Jeden neuen Wunsch **sofort als Task anlegen**
   (`TaskCreate`), auch wenn er erst später drankommt. Der Task-Backlog ist die dauerhafte
   Merkliste; nie einen Wunsch nur „im Kopf" behalten.
2. **Immer den Stand melden.** Bei jeder Nutzer-Nachricht und an Meilensteinen kurz zeigen:
   **✅ durch · 🔄 in Arbeit · ⏭️ als Nächstes** (inkl. Reihenfolge). Der Nutzer soll nie raten
   müssen, was passiert.
3. **Ideale Reihenfolge selbst wählen & umsortieren.** Reihenfolge nach Abhängigkeit/Aufbau
   bestimmen (baut B auf A auf, kommt A zuerst) — Tasks dürfen umgeschoben werden. Kurz begründen.
4. **Parallel zur Pipeline arbeiten.** Während eine CI-Pipeline läuft, **nicht idlen**: schon die
   nächste Aufgabe entwickeln. Dafür einen **git-Worktree** (isolierte Kopie) nutzen, damit der
   offene PR-Branch sauber bleibt; nach dem Merge des laufenden PRs den Zweig zurücksetzen und die
   vorbereitete Arbeit übernehmen (cherry-pick).
5. **Ein PR pro Feature**, jeweils voller Workflow (changes.txt → PR + Auto-Merge → grünes CI →
   Merge → **Release cutten**). Nie mehrere unfertige Features in einem PR mischen.
6. **Nur bei echtem Blocker fragen.** Sonst „nach bestem Wissen & Gewissen" entscheiden, die
   Annahme im PR/Chat protokollieren und weitermachen. Fragen sammeln statt einzeln unterbrechen.
7. **Limit/Reset überbrücken.** Wird ein Nutzungs-/Zeitlimit erreicht, per `ScheduleWakeup`
   (o.ä.) einen Wecker auf den Reset-Zeitpunkt stellen und **automatisch weitermachen** — der
   Nutzer soll nur bei Bedarf reinsprechen müssen.
8. **Abschluss-Zusammenfassung.** Wenn der Backlog leer ist (oder auf Nachfrage): kompakte
   Übersicht aller erledigten Punkte + **offene Fragen/Klärungsbedarf/Wünsche** an den Nutzer.

## Key conventions

- **Offline-First** (`sw.js` + `state.net` + Konflikt-Reconcile): Die PWA ist offline (Flugmodus) voll spielbar. **`sw.js`** liefert die App-Shell **cache-first** mit Navigations-Fallback auf `index.html` (Home-Icon startet offline zuverlässig), alle gleich-origin GET-Assets als **stale-while-revalidate**, Fremd-Origin (Firebase) wird durchgereicht; Precache **einzeln** (`Promise.allSettled`) + **atomarer Swap** (alte Caches erst löschen, wenn der neue die Shell hat) → kein Aussperren nach misslungenem Update. **JEDES neue `js/`-Modul MUSS in die `ASSETS`-Liste** (sonst offline nicht ladbar — passierte mit `session.js`); `test/unit/precache.test.js` erzwingt das jetzt REKURSIV (inkl. `js/games/<id>/`) und prüft zusätzlich die Gegenrichtung (kein Pfad in `sw.js`, den es nicht mehr gibt). Cache-Version bumpt `build.js` pro Release. **Manuelle Update-Prüfung**: Klick auf die Version im Hauptmenü → `checkForUpdate()` (app.js) stößt `reg.update()` an; wartet danach ein neuer Worker, bietet ein Dialog den Neustart an (`restartForUpdate` → `SKIP_WAITING`-Message an sw.js → `skipWaiting()` → `safeReload`). Weiterhin KEIN automatischer Laufzeit-Update-Flow — ohne Nutzeraktion übernimmt eine neue Version erst beim nächsten Kaltstart. **`state.net`** (`'online'|'offline'|'reconnecting'`, `initConnectivity()` aus `navigator.onLine`+Events+visibilitychange) → `isOnline()`; netzabhängige Aktionen (Coop/Race/Freunde) offline `disabled` + Guard statt Firebase-Timeout; Home zeigt `.offline-chip`; `onReconnect()` triggert `reconcileSession`+`doSyncNow`. Solo/Training sind komplett lokal. **Versions-Mismatch**: `account.isDivergent()` (rein, unit-getestet) erkennt formale Divergenz (lokal UND Cloud seit `syncedRev` geändert); `reconcile()` löst sie INHALTLICH auf — verlustfreier Auto-Merge (`mergeSnapshots`, s.o.) ⇒ `decision:'merged'` still; NUR bei abweichendem Geld-Saldo (`walletBalanceDiffers`) ⇒ `decision:'conflict'` → app.js `openVersionMismatch`/`resolveVersionMismatch(choice)` zeigt den `.mismatch-modal`, die Wahl betrifft NUR das Guthaben (Rest bleibt gemergt); `account.resolveConflict(choice)` wendet an und sichert die unterlegene Seite als Backup (`saveConflictBackup`, nie still gelöscht), dann `safeReload`. **Grenze:** der Erststart muss einmal online sein (GitHub Pages cached erst dann).
- **Minimalistisches Design** (Nutzerwunsch: „schlanker, kleiner, nicht alles ausfüllen, mehr Luft"). Leitlinien für neue UI: Inhalte in **schmalen, zentrierten Spalten** statt von Rand zu Rand (Startseite `.home-actions` max. 300 px, Auswahl-Screens `.setup-slider` max. 320 px — der morphende Hintergrund bleibt vollflächig); **leichte Schatten** über `--soft-shadow` statt des früheren schweren `0 2px 10px var(--shadow)`; Nebenflächen **flach mit Haarlinie** (`--hairline`) statt Schatten; Knöpfe `.btn` 12/14 px Innenabstand, `.icon-btn` 40 px, Werkzeug-Knöpfe im Spiel 52 px (Tippflächen bleiben ≥ 40–44 px). Auf der Startseite zeigen die Modus-Knöpfe (`.mode-btn`) nur ihren Namen, Statistik/Verlauf sind dezente Textknöpfe, der Titel steht einzeilig und klein, das Hintergrundmotiv ist nur ein Hauch (`opacity .035`). Hinweis: `--line` war nie definiert (fiel auf `currentColor`/nichts zurück) — für Linien `--hairline` nehmen.
- **Feste Positionen, keine überlappenden Texte** (Nutzerwunsch: „Schriften überlappen sich niemals, Buttons haben feste Positionen und verschieben sich nie dynamisch"). Die Startseite ist ein RASTER von oben (`.home`, `grid-template-rows: auto auto auto minmax(0,1fr) auto` = Marke · Modus-Knöpfe · Fortsetzen · Luft · Fußzeile); ihr Abstand nach oben hängt NUR an der Bildschirmhöhe (`padding-top: clamp(52px, 52px + (100dvh - 600px) * .4, 220px)`), nie am Inhalt. Vorher war die Spalte vertikal zentriert: ein erscheinender Fortsetzen-Knopf (oder ein Spielwechsel mit anderem Fortsetzen-Angebot) schob Scheibe, Titel und ALLE Knöpfe um ~30 px. Der **Fortsetzen-Bereich** (`.home-resume`, `<transition name="rfade">` ohne Spiel-Key) steht deshalb UNTER den Modus-Knöpfen und wächst in den freien Platz; reicht der auf sehr kleinen Geräten nicht, scrollt die Seite — verschoben wird nichts. **Fußzeile** `.home-foot` = festes Dreier-Raster (Offline-Chip links, Version mittig), der Chip schiebt die Version nicht (oben lag er über dem Serien-Zähler). **Ecken-Marken** (`.badge-soon`, `.badge-endless`) sitzen auf der Oberkante des Knopfs, nie in seiner Textzeile (mittig rechts überdeckten sie in längeren Sprachen die Beschriftung). Ein- und Überblenden (`fadein`, `rfade`) animieren nur noch die Deckkraft, nichts rutscht nach. Im Querformat: Marke links (Version darunter), Knöpfe rechts mittig, Fortsetzen darunter. E2E `fixedlayout.spec.js` misst Positionen vor/nach Fortsetzen + Offline + Serie und nach dem Spielwechsel und prüft alle sichtbaren Texte paarweise auf Überlappung (clip-bewusst, auch fr-FR). **Neue Elemente auf der Startseite brauchen einen festen Platz** — nichts darf andere Knöpfe verdrängen.
- **Native-App-Gefühl: die Seite steht fest.** `html, body { overflow: hidden; touch-action: pan-x pan-y; overscroll-behavior: none }` — die SEITE selbst scrollt, verschiebt und zoomt nie; gescrollt wird nur in Bereichen, die das ausdrücklich dürfen (`.screen` senkrecht, das gezoomte Brett, Modals). `touch-action` ohne `pinch-zoom` sperrt Browser-Zoom; iOS-Safari ignoriert `user-scalable=no`, deshalb fängt ein Skript im `<head>` `gesturestart`/`gesturechange`/`dblclick` ab. **`.screen` hat `overflow-x: hidden`**: `overflow-y:auto` machte die x-Achse implizit mit scrollbar — EIN überstehendes Element (der Name des Nachbarspiels unter der Scheibe, +46 px) machte die ganze Startseite seitlich verschiebbar (gemeldet: „fühlt sich an wie eine Website"). Auf Touch-Geräten keine Scrollbalken (`scrollbar-width:none` / `::-webkit-scrollbar`). **Die Startseite passt ohne Scrollen** auf 320×568 bis 430×932: Scheibe und Abstände skalieren mit `dvh` (`--gw: clamp(76px, 12.5dvh, 112px)`, `gap: clamp(8px,2dvh,16px)`), unter 620 px Höhe wird dichter gepackt. Alles, was absichtlich übersteht (Scheibe), schneidet am EIGENEN Rand ab (`overflow:hidden`), nie am Bildschirmrand. E2E `nativefeel.spec.js` misst Seite UND Startseite auf sechs Handy-Größen (kein Überstand in x/y, `overflow:hidden`, `touch-action`) und nach einem Spielwechsel.
- **Kopfleiste im Spiel = EINE Zeile.** Jede Kopf-Zeile ist auf dem Handy Brettfläche, deshalb trägt `.topbar.game-top` alles: Leben, Zeit, Endlos-Chips, Werkzeuge (`.zoomctl` in `.top-actions`) und Pause. Die Info-Chips teilen sich die zweite Zeile mit dem Fortschrittsbalken (`.meta-row` = `.meta-chips` + `.progress-row`), der die Breite nicht braucht — die frühere eigene `.game-meta`-Reihe ist damit ersatzlos weg. Gemessen: das Brett beginnt bei **88 statt 150 px**, die Kopfleiste ist 48 statt 60 px hoch. **Wo die HÖHE die bindende Achse ist, wächst die Zelle dadurch wirklich** (360×560: Mittel 30→35, Bismillah 19→22, R.I.P. 18→21; Handy quer 740×360: 29→30 / 18→19 / 17→18). Auf den üblichen Hochformat-Handys (360×640 und größer) ändert sich die Zellgröße NICHT, weil dort die BREITE begrenzt (`cellPx = min(idealW, idealH)`, s. `recalcCellSize`) — gewonnene Höhe ist dort Luft, nicht Fläche. **Neue Knöpfe gehören in die Kopfleiste, nicht in eine neue Reihe.** `flex-wrap` auf der Kopfleiste ist der Notausgang für die vollste Lage (Endlos + Coop + Chat, auf 360 px bricht sie dort um); die Werkzeuge bleiben dabei per `margin-left:auto` rechtsbündig. Der Zoom bildet ein ABTEIL (`.zoomctl > .toolgrp`) mit sichtbar eigener Fläche; der nur zeitweise sichtbare Zurücksetzen-Knopf sitzt in einem `.tool-slot` FESTER Breite, der seinen Platz auch leer behält — bewusst kein ausgegrauter Knopf, sondern leerer Platz, damit − / + beim Ein-/Ausblenden nie unter dem Finger wegwandern. Beide E2E in gameplay.spec.js („die Kopfleiste bleibt einzeilig und laesst dem Brett Platz", „der Zoom-Reset verschiebt minus und plus nicht") halten Höhe, Umbruchfreiheit, Brettanfang und Positionstreue mit gemessenen Kästen fest.
- **Zahlen in der Kopfleiste brauchen FESTE Kaesten.** `font-variant-numeric: tabular-nums` macht nur die ZIFFERN gleich breit, nicht ihre ANZAHL: beim Sprung 9:59 → 10:00 kam ein Zeichen dazu, der Zeit-Kasten wuchs um ~10 px (gemessen 37 → 47 → 57), die ganze Kopfzeile wurde breiter und die Zoom-Leiste rutschte „eine Etage tiefer" (gemeldet). Deshalb (a) `.hud-item.timer { min-width: var(--timebox) }` mit `--timebox: 7ch` auf `.screen.game` — fester Platz bis „999:59" (über 16 h reiner Spielzeit), Text darin zentriert; `ch` = Breite der Ziffer 0, der Doppelpunkt ist schmaler, die Reserve liegt also über dem Bedarf.
